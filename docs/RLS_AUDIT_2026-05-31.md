## Findings critiques identifiés

| Source | Risque identifié | Remédiation appliquée |
| --- | --- | --- |
| `supabase/backup.sql` | Policy legacy `Anyone can read orders` avec `USING (true)`, exposant les commandes. | Remplacée par `orders_select_own_or_admin` dans les migrations de durcissement. |
| `supabase/backup.sql` | Policy legacy `Public profiles are viewable by everyone.`, exposant les profils clients. | Remplacée par `profiles_select_self_or_admin`. |
| `supabase/backup.sql` | Trigger `handle_new_user` attribuant `admin` via email contenant `admin`. | Trigger durci : nouveau profil toujours créé avec rôle `customer`. |
| Tables commerce futures | `payments` et `shipments` non définies ou non protégées, risquant d'exposer PSP, tracking et statuts de livraison. | Migration `20260629_secure_sensitive_tables.sql` : création additive, RLS activée, lecture propriétaire/admin uniquement, mutations réservées admin/service role. |
| Tables data/IA futures | `events`, `ai_conversations`, `audit_events` non définies ou non protégées, risquant d'exposer analytics, conversations IA et traces sensibles. | Migration `20260629_secure_sensitive_tables.sql` : RLS activée, insert propriétaire pour events/IA, lecture propriétaire/admin, audit admin uniquement. |

## Baseline RLS après remédiation

- `profiles` : lecture soi-même ou admin, insertion de son profil client, mise à jour limitée aux champs non rôle.
- `orders` : lecture propriétaire ou admin, insertion propriétaire, mise à jour admin.
- `order_items` : accès dérivé de la commande parente.
- `payments` : lecture propriétaire de la commande ou admin ; mutation par admin/service role pour futur PSP/webhooks.
- `shipments` : lecture propriétaire de la commande ou admin ; mutation par admin/service role.
- `events` : insertion/lecture de ses propres événements ; admin peut auditer.
- `ai_conversations` : insertion/lecture de ses propres conversations ; admin peut auditer.
- `audit_events` : lecture/mutation admin uniquement côté client authentifié ; service role autorisé pour journalisation serveur.

## Scénarios de test manuel à exécuter sur Supabase cible

1. Client A connecté ne peut pas sélectionner une commande, un paiement, une livraison ou une conversation IA appartenant à Client B.
2. Client non connecté ne peut lire aucune ligne `profiles`, `orders`, `order_items`, `payments`, `shipments`, `events`, `ai_conversations`, `audit_events`.
3. Client connecté peut lire ses propres commandes, lignes de commande, paiements et livraisons.
4. Client connecté ne peut pas insérer/modifier directement `payments`, `shipments` ou `audit_events`.
5. Admin peut lire les profils, commandes, paiements, livraisons, événements, conversations IA et audit events.
6. Le webhook PSP côté serveur utilise le `service_role` pour insérer/mettre à jour `payments` sans exposer cette capacité au client.
7. Le trigger `handle_new_user` crée tout nouveau compte en rôle `customer`, y compris une adresse email contenant le mot `admin`.
